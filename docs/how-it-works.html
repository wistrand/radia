How Radia works

Six ideas, and the whole runtime falls out of them: records are immutable, claim state is not, patterns are data, a claim is a fenced lease, results are records too, and every mutation is in the log before the caller hears about it.

1. Records

Tasks, facts, requests and results are the same thing.

A record is JSON with a kind. Nothing distinguishes a unit of work from a piece of knowledge except whether anybody claims it, which is decided by the kind's declaration rather than by the writer.

POST /v0/records
{ "kind": "task",
  "body": { "op": "upper", "input": "hello" },
  "parentIds": ["01KZ6X7QXBSV7PS9A9WS8VT6EJ"] }

The server assigns everything that carries authority: who created it, when, the content hash, the classification labels, the delegation chain. A client submits claims about its work; the runtime decides what those claims are worth. Fields like confidence are the client's opinion, and created_by is not.

Immutable after commit. There is no update. A correction is a new record naming the old one as a parent, so the history of a fact is a walk rather than a diff.

2. Patterns are data, never code

A stored pattern can be inspected, authorized and refused.

A worker says what it handles with the same JSON language a query uses: equality, $gt, $in, $exists, $any, $or. There is no $regex, no $where, no expression evaluation, and there never will be. The tuple-space systems this descends from shipped code to the server for flexible search; a decade of security experience since sides against that, especially in a space shared by agents that do not trust each other.

Because a pattern is data, it can be stored and asked about. Workers publish what they listen for, so POST /v0/ops/dry-run answers who would receive this record before the record is written.

the same shape, three uses
// claim work
{ kind: "task", match: { op: "upper" } }

// read facts
{ kind: "result", match: { score: { $gt: 0.8 } } }

// scope a grant
{ kind: "document", match: { classification: "public" } }

3. Claiming work

One winner, a renewable hold, and the work comes back if you die.

Claiming is competitive. Several workers may match the same record; exactly one gets it, and the loser is told so rather than handed a duplicate. Ranking is by priority, then by how long the record has been eligible, then by id, so the order is deterministic and the same on every storage backend.

4. Fencing, so a slow worker cannot overwrite a fast one

At-least-once delivery means two processes can run the same task.

A lease carries an epoch. When a lease expires and another worker claims the record, the epoch increases. The original worker may still be running: it has no way to know its lease lapsed until it tries to settle, and at that point the epoch it holds is stale and its write is refused.

Idempotency is checked before the fence. A retry of an operation that already succeeded replays the stored response instead of reporting a lost lease. Reversing those two checks turns a successful ack into a false failure, which is the kind of bug that only appears under a network that drops a response.

5. Lineage is data, not a log

Provenance is not authority, and the two are kept apart on purpose.

Every record can name parents. That edge is causality: this result came from that task, this fix was written after reading that failure. It is queryable in both directions, up through ancestors and down through children, and it is what classification labels travel along.

What lineage never does is grant anything. Deriving a record from a privileged one gives the deriver no authority. Authority travels on a separate chain that the runtime builds from the lease that was actually claimed, so an agent cannot promote itself by naming a powerful parent.

6. The event log, and the chain over it

Every mutation is in the log in the same transaction that performed it.

Watches are served from the log, so a worker is woken rather than polling. The cursor is gap-free even when transactions commit out of order, which matters the moment more than one runtime instance shares a database.

Once an event is final, it is sealed into a hash chain. The hash covers the event and the record's content hash, so editing a body directly is caught rather than leaving a chain that still verifies. Each link is signed under a key that lives beside the database rather than in it.

What a chain in the same database buys. It detects corruption, partial restores, and edits by somebody who did not know to recompute. It does not, by itself, detect an adversary with write access, because they can recompute every hash. The signature is what closes that, and only for as long as the key is somewhere the database is not.

7. Artifacts, and the one thing that can be erased

Bytes never travel inside a record.

An image, an audio clip or a generated file is stored content-addressed in a blob store, and the record carries {digest, mediaType, size}. That keeps matching, paging and every size assumption intact.

It also creates the one place where deletion is possible. Records are immutable, so a body can never be erased; a payload is out of line, so it can be destroyed while the record, its id, its lineage and the event log survive. Anything that may need erasing has to be an artifact, whatever its size.

This protects high-entropy payloads only. The plaintext hash stays in the record, so anyone holding a candidate can confirm the content was there. A destroyed document is gone in every practical sense; a destroyed password is merely unreadable.

8. One runtime, three storage backends

Embedded is never a semantically weaker cousin of Postgres.
