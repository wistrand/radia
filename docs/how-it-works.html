How it works

The easiest way to understand this is to follow one document. It gets posted, a worker claims it, the worker crashes halfway through, another one picks it up, and a summary comes out the other end. Every part of the runtime shows up somewhere in that story.

Somebody posts a document

A record is JSON with a kind. That is the whole data model. The kind is a label like document or summary, and the body is whatever you want to say.

posting one
{ "kind": "document",
  "body": { "type": "pdf",
            "classification": "public",
            "url": "https://example.com/filing.pdf" } }

Notice what is missing. There is no destination, no queue name, no worker id. You are not sending this anywhere. You are putting it down where interested parties can find it.

The runtime fills in the parts that carry weight: who posted it, when, a hash of the contents. Your process does not get to claim it was somebody else, because those fields are not yours to write. Anything you do send that is a matter of opinion, like a confidence score, stays your opinion and is stored as such.

A worker has already said what it wants

Somewhere else, a summarizer is running. When it started, it described the shape of record it handles, in the same little JSON language you would use to search:

what the summarizer listens for
{ kind: "document", match: { type: "pdf" } }

You can say more than equality. Ranges, "one of these values", "this field exists", "any element of this array matches". What you cannot do is write code. There is no regular expression operator and no expression evaluator, and there is not going to be one.

That restriction has a history. The systems this idea comes from, going back to the 1980s, let you ship a search function to the server, and it was considered a feature. In a space shared by agents that do not trust each other, a search predicate that is code is a way to run code on somebody else's machine.

Keeping patterns as plain data buys something else, too. Because a pattern is just a value, you can store it, ask questions about it, and refuse it. Workers publish what they are listening for, so you can ask the space "if I posted this, who would get it?" before you post anything.

The worker claims it, and gets a deadline

Claiming is competitive. If you are running four summarizers, all four match this document and exactly one gets it. The other three are told there was nothing for them rather than handed a copy, so the same document is never worked twice at the same moment.

What the winner gets is a lease: the document is theirs, but only for a while. The lease has a deadline, and the worker can push the deadline back for as long as it is genuinely working.

Then the worker dies

Somebody deploys, or the machine goes away. The summarizer is gone in the middle of a document and nobody told the space anything.

Nothing special happens, which is the point. The lease deadline passes, the document goes back to waiting, and the next summarizer claims it. You lose the work in flight and nothing else.

There is a subtlety here worth understanding, because it is the one thing that trips people up. A dead worker and a slow worker look identical from the outside. If your summarizer is merely stuck behind a very slow model call, its lease can expire while it is still running. Now two processes are working on the same document, and eventually both will try to answer.

This is why work that touches the outside world needs care. Summarizing the same document twice is harmless. Sending the same email twice is not, and that is your problem to handle at the point where the email goes out, not something the runtime can do for you.

The summary comes back

The second worker finishes and answers. Two things happen at once: the document is marked done, and a new record appears holding the summary, with the document listed as its parent.

That summary is an ordinary record, so anything watching for summaries picks it up. If you later want a step that files summaries into a report, you write it and start it. You do not go back and modify the summarizer to call it, because the summarizer has nobody to call.

If the answer never arrives, and the worker just keeps failing, the document is eventually set aside rather than retried forever. You can look at what is sitting there and put it back once you have fixed whatever was wrong.

What all this leaves behind

Every one of those steps was written to a log as it happened, inside the same database transaction that made the change. Not written afterwards, and not written by an observer that might have missed something. If the change happened, the log entry happened.

Two things fall out of that. Workers can be woken by the log rather than polling, and you can replay what occurred without reconstructing it from application logs. When somebody asks why a particular summary says what it says, you follow the parent links back to the document, and the document back to whatever produced it.

For the case where somebody might have reason to doubt the record, finalized entries are sealed into a chain, each one covering the entry before it and the contents of the record it refers to. Editing a document in the database after the fact breaks the chain rather than leaving something that still looks consistent.

Be honest about what a chain like this can prove. It catches corruption, a bad restore, and someone editing a row without knowing to recompute the rest. On its own it does not catch a determined attacker with database access, because they can rebuild the whole chain. Signing each link with a key kept outside the database is what closes that, and only while the key stays somewhere the database is not.

When the payload is too big to be a record

The document in this story was a URL. Suppose it is the PDF itself, or an image a model generated, or an hour of audio. That does not go in the record. It is stored separately, addressed by the hash of its contents, and the record carries the hash, the media type and the size.

Partly this is practical: a megabyte of base64 in a body makes matching slow and pages unpredictable. But it also creates the one place in the system where something can actually be deleted. Records are permanent by design. Payloads are not, so if a customer asks you to erase their file, you can, and the record, its history and everything that referred to it survive.

This works for real documents and not for short secrets. The hash of the original stays in the record, so anyone holding a guess can check whether it was the thing you deleted. A deleted contract is gone for all practical purposes. A deleted password is merely unreadable.

Where all this actually lives

One process owns the database, and everything else talks to it over HTTP. That process is the only thing that has to get the concurrency right, which is why claiming, fencing and authorization are all in one place instead of spread across every worker you write.
