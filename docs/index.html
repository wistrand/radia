Agents claim work.
Nobody wires them together.

Agents in Radia do not call each other. One writes a record into a shared space. Another has declared the pattern of record it handles, and the runtime hands each record to one worker whose pattern matches. A record is JSON with a kind, and it carries no destination, no queue name, no worker id; the whole of a worker's registration is a pattern like { kind: "document", match: { type: "scan" } }. So the day you want scanned PDFs handled, you start a worker that says that, and stop: the summarizer that posts documents never learns it exists.

$ deno task dev
Starts a space and a web console on 127.0.0.1:7788. Nothing to install, no database to set up.

The wiring is the thing that gets expensive

Every agent framework starts the same way. You write an agent, give it a list of tools, and it works. Then you add a second agent, and now the first one needs to know about it. Then a third, and you are maintaining a graph of who calls whom. Adding a capability means editing the code of everything that might want it, and shipping all of it together.

Radia takes the calls out. Workers do not hold references to each other. They post records into a shared space, and they claim records by describing the shape they handle. Your OCR worker says "I take documents where type is scan", and that sentence is the whole of its registration.

What you get for that is a system where deployment is the only integration step. Start the worker and the capability appears. Stop it and the capability goes away, and the documents it would have handled sit in the space waiting for something that can.

Now suppose one of those documents is confidential

Your summarizer sends text to a model hosted somewhere else. You are happy for it to read the public filings. You are not happy for it to read the ones marked confidential, and you would like that to be true even if somebody writes a buggy agent next week.

Because the document is a record rather than an argument to a function call, the runtime can look at it. A grant says which principal may claim which kind, and it can carry a pattern that the record's own contents have to satisfy.

this agent can only ever claim public documents
{ "principal": "agent:summarizer",
  "kind": "document",
  "operations": ["take", "query"],
  "pattern": { "classification": "public" } }

The check runs inside the claim itself, so the worker cannot skip it, forget it, or be talked out of it by a prompt. A confidential document is simply never handed over. From the summarizer's point of view there was nothing to claim.

Durable execution engines dispatch by function name and treat the payload as an opaque blob, so there is no point in their design where this question can be asked. That gap is the reason this project exists. How authorization works →

A record never changes. Its claim state does.

When the summarizer finishes, it does not update the document. It writes a new record, a summary, that names the document as its parent. The document is exactly as it was.

That summary is a record too, so a third worker can match on it without anybody arranging the handoff. A step that collects results never has to be told which workers produced them. This is what makes fan-in work when the workers involved were written by people who have not met.

Getting started

One command starts a space with storage, a web console and a credential already provisioned. From there you can drive it from the shell.

post some work, claim it, answer it
$ deno task dev                     # space + console, in one process
$ deno task compile                 # -> ./radia; put it on your PATH
$ radia put document '{"type":"pdf","classification":"public"}'
$ radia take document --lease 30 --json > claim.json
$ radia ack - --result-kind summary --result '{"text":"..."}' < claim.json

Run it from the checkout: compile it as above, or deno run -A src/main.ts <verb> directly. The npm and pip packaging is built but unpublished, so nothing installs radia for you yet and npx radia does not work today.

The CLI has no private door into the runtime. Every one of those commands goes through the same public API your own code would use, which is a deliberate constraint: if the CLI can do it, so can you. The same is true of every other way in: the TypeScript and Python SDKs, the web console, and an MCP adapter that lets a model you already talk to browse the space, all clients of the same frozen API.

Here is that summarizer as a real worker, and this is the whole file.

summarizer.ts
import { RadiaClient } from "radia";
import { agentLoop } from "radia/loop";

await agentLoop(new RadiaClient(url, { token }), {
  name: "summarizer",
  patterns: [{ kind: "document", match: { type: "pdf" } }],
  handle: async (rec) => ({
    kind: "summary",
    body: { text: await summarize(rec.body) },
  }),
});

The loop handles the lease, renews it while you work, and retries the record if your process dies partway through, with no server to register with and no address to configure. Kill it mid-document and the document goes back to waiting.

What is built

All of the first milestone and a good part of the second, running on three storage backends: SQLite and PGlite for local work, and real Postgres when you want several instances. The same test suite runs against all three.

Coordination

Posting, claiming, answering and retrying work. Leases that survive a crash, and delivery that never silently drops a task.

Authorization

Grants scoped to a kind and a pattern, labels that follow data through the system, credentials that replace themselves so nobody signs in twice, and sign-in from an identity provider you already run. How it works →

Large payloads

Images and files live outside the record, addressed by content hash, and can be destroyed later without breaking the history.

Seeing what happened

An event log, lineage queries, a web console, a tamper-evident chain over the log, and OTLP export into Jaeger or Tempo: threads become traces, work attempts become spans. What it can tell you →

Meeting the world

Multi-file trees an agent can write, run in a jail, serve to a browser, and clone with git. Built on the above, outside the runtime. Workspaces →

It is not production ready, and nobody but the author has used it yet. Every item from two code audits is closed and nothing above low severity is open, but the packages are unpublished, so today this runs from a checkout.
Radia is named for Radia Perlman, whose Spanning Tree Protocol showed independent nodes building a shared structure with no central controller.
