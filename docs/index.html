Agents claim work.
Nobody wires them together.

Agent frameworks wire agent A to call agent B. Radia replaces the wiring with a shared space: agents post work, and whichever agent said it can handle that work claims it under a lease. Start a worker and the system gains a capability, with no code change anywhere else.

$ deno task dev
Starts an embedded space and a web console on 127.0.0.1:7788. No database to install.

Every task is a record, so you can authorize one at a time

May this payload reach this step?

Durable execution engines dispatch by function name and treat payloads as opaque blobs. There is nowhere in that model to ask whether a particular payload may reach a particular step. Radia moves the question into the substrate: a grant scopes a principal to a kind and a pattern, and the pattern matches the record's body.

a grant, which is itself a record
{ "principal": "agent:summarizer",
  "kind": "document",
  "operations": ["take", "query"],
  "pattern": { "classification": "public" },
  "scope": { "taint": ["net"] } }

That agent may claim public documents and nothing else, and it may claim work whose lineage touched the network but not work that touched the filesystem. The restriction is enforced inside the claim transaction, so a worker cannot decline to apply it.

A record has an immutable half and a mutable one

Content never changes. Claim state does.

Because results are records too, the answer one agent acks is matchable by the next. A fan-in step never has to know which agents produced its inputs.

Getting started

run a space, then talk to it
$ deno task dev                     # embedded space + web console
$ radia put task '{"op":"upper","input":"hi"}'
$ radia take task --lease 30 --json > claim.json
$ radia ack - --result-kind result --result '{"out":"HI"}' < claim.json

The CLI has no privileged path into the runtime. Every verb goes through the same public /v0 API an external client uses, so anything the CLI can do, your code can do.

a worker, in full
import { agentLoop, RadiaClient } from "radia/sdk";

await agentLoop(new RadiaClient(url, { token }), {
  name: "upper",
  patterns: [{ kind: "task", match: { op: "upper" } }],
  handle: (rec) => ({
    kind: "result",
    body: { out: rec.body.input.toUpperCase() },
  }),
});

The loop supplies the fenced lease, the heartbeat, idempotency keys and at-least-once delivery. Kill the process mid-task and the work becomes claimable again.

What is built

All of M0 plus a growing M1 slice, on three storage backends (embedded SQLite, embedded PGlite, and real Postgres) behind a frozen wire contract that is checked against the router in both directions.

Coordination

put, take, ack, nack, release, renew. Fenced leases, idempotency, dead-letter, SSE watches.

Authorization

Kind- and pattern-scoped grants as records, run-token bootstrap chain, delegation context, taint labels.

Artifacts

Content-addressed blobs, short-lived download capabilities, optional encryption, erasure by shredding.

Inspection

Transactional event log, lineage and graph queries, mined flows, a tamper-evident hash chain.

Not production ready, and there is no second user. Every audit package is closed and no P0 or P1 is open; what remains is a low-severity batch. The npm and pip packaging is built but unpublished, so today this runs from a checkout.
Radia is named for Radia Perlman, whose Spanning Tree Protocol showed independent nodes building a shared structure with no central controller.
