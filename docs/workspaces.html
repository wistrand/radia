Where the work meets the world

Records are a fine way for agents to talk to each other. They are a poor way to hand a three-file website to a person, or to run a program that expects a directory. A workspace is the seam: a multi-file tree an agent can write, run, look at and export as a real git repository. None of it is in the runtime.

An agent that writes code needs somewhere to put it

A single-file evaluator gets you further than you would expect and then stops dead. Real work is a project: write a few files, run the thing, read the error, fix one line, run it again. The loop is not the hard part. The missing part is somewhere for the program to live between iterations.

That is a gap in what agents can reach, not in the coordination model underneath. A round trip through the space costs about thirty milliseconds and a sandbox start about twenty-seven, against a model turn of one to ten seconds. Routing this loop through records costs roughly one percent of an iteration; the medium was never the constraint.

It is a convention, not a feature of the runtime

The design stays small because of one refusal. Radia has no idea what a file is. It has no idea what a path, a file mode or a directory is. Nothing in the runtime knows the word workspace.

A workspace is a record whose body happens to list files, plus one artifact per file, plus a projection that says which version is current. Every one of those is a primitive that already existed for other reasons. The convention lives one tier out, in a library that talks to the space through the same public API your own code would use.

A test greps for the dependency rule: an extension that reached into the runtime fails the build. That direction is what keeps the runtime from slowly growing opinions about filesystems, and it is why exporting a workspace to git is an ordinary client command instead of a feature of the server.

Two things here are specified, not merely implemented. The tree digest and the path validator cross a trust boundary: a verdict about a tree is comparable across languages only if every implementation hashes it identically, and a path rule that differs between implementations is a hole rather than an inconsistency. Both ship with a conformance suite that any implementation in any language has to pass.

Workspaces are one convention on a longer shelf

The same tier holds every other convention more than one application wanted and the runtime had no business knowing. Each is a small library over the same public API, and each earns its place by answering a question the applications kept re-answering badly:

  • Tool workers. A worker advertises each tool as a record carrying its schema and description, an agent builds its tool list by watching for those records, and a call routes to whichever worker claimed that tool's name. Adding a worker adds a capability with no configuration anywhere, which is the promise on the front page made concrete. A failed call comes back as an answer, never as silence, so a caller is told what went wrong instead of waiting out its deadline.
  • A model turn as records. The chat's conversation loop does not live in the terminal: the client writes one request and renders whatever arrives, while workers emit each next step as a record. Kill the terminal mid-turn and the turn finishes without it. Model tiers are records too, so the router and the escalation ladder read the same list.
  • Sealed conversations. Prose is encrypted end to end while the records still route, because nothing ever matched on prose. The keys live in destroyable payloads, which is what gives an immutable history an erasure path. The chat uses it →
  • Compartments. Containment for a class of data: a dedicated kind plus pattern-scoped grants. Outside it, writes are refused by construction, and getting data out is reserved to a principal deliberately granted both sides.
  • Traces for your existing tools. Threads export as OTLP traces, attempts as spans; Jaeger or Tempo then renders what happened without learning anything about records.

The rest of this page walks the largest of them: the tree itself, running code from it, and promoting a tree to be an agent's code.

What a tree actually is

One record holds the manifest: a name, a tree digest, the version it was based on, and a list of files. Each entry is a path, a mode, a content hash and the artifact holding the bytes.

a workspace record
{ "name": "landing-page",
  "treeDigest": "t1:9f2c...ade1",
  "basedOn": "01JB2Q7X4KJ8ZN0R5V3M9WPHTC",
  "files": [
    { "path": "index.html", "mode": "100644", "digest": "sha256:4b1e...", "artifactId": "01JB2..." },
    { "path": "style.css",  "mode": "100644", "digest": "sha256:c70a...", "artifactId": "01JB2..." },
    { "path": "cat.png",    "mode": "100644", "digest": "sha256:8ee3...", "artifactId": "01JB2..." }
  ] }

Editing the tree writes a new manifest that points at the version before it: history is a chain of records, not a mutable directory. Bytes are shared by content, so changing one character in one file stores one file, not a tree. Two agents editing the same base produce two successors and you can see that they diverged, which beats one of them quietly winning.

A file does not have to be written to be added. An image the agent generated earlier is already an artifact, so attaching it to a tree moves no bytes at all: the manifest points at what is already there, and the artifact becomes a data parent of the tree; whatever labels it carries follow it in.

radia workspaces
NAME          FILES  VERSIONS  TREE            OWNER
landing-page      3         7  t1:9f2cade1a4…  human:alice
scraper           9        22  t1:07b3e5c918…  human:alice

Paths are validated on the way in, not on the way out, and the placement is the security decision. There is no filesystem inside the space, so a path is just a string in a record until something materialises it, and every rule about what a path may contain gets applied at the moment it is written. Materialising the tree revalidates anyway, and checks that each resolved file really landed inside the directory it was supposed to.

Running what is in it

A tree is only interesting if something can execute it, and executing model-written code is a question about isolation rather than about languages. Two jails ship. One runs JavaScript in a subprocess with no permissions at all, safe by the absence of every flag. The other runs any interpreter inside bubblewrap, safe by the presence of the right ones.

Those are not equivalent, and the difference is not something to paper over in a sentence on a web page. So a jail is a record: it states what it actually guarantees, an operator declares it, and the worker probes it before serving anything. A bubblewrap jail missing one flag can reach the network while its record claims it cannot. Nothing is advertised on the strength of a claim, only on a passed probe.

Which means the answer to "what can this space run" is discovered rather than configured. A runner publishes run_javascript or run_python only where its backend probed clean, so a language the host cannot isolate is simply absent from the tool list instead of failing after a turn has already committed to it.

The process that runs the code holds no credential. The worker that spawns jails can start two specific binaries and reach the space, and nothing else. The child it spawns gets no permissions and no token. Compromising the dangerous half yields a process that can print bytes to its parent.

One caveat, found by measurement: a permission model bounds the calls a program makes, and in Deno it does not bound what the module loader reads. A jail with no filesystem grant can still import any JSON or JavaScript its user can read. So the filesystem boundary is a second mechanism underneath the permission one, a mount namespace on Linux and a Seatbelt profile on macOS, and each jail record says which one bounds it rather than leaving a reader to assume.

Code that runs this way still has to produce something, and the answer is the same tree idea pointed the other way: a run saves files, into a directory that becomes a new version of an output workspace when the run ends. That is what makes a chart, a PDF or a compiled binary expressible at all, since a record holds JSON and the channel back to the space carries lines of text. It also explains a rule that looks arbitrary until you hit it: a run never writes into the tree it runs from. That tree is the code, shared between everything running the same version and named by its own digest, so a program editing it would change what that name refers to while its neighbours were still reading it.

Promoting it: an agent whose code is a tree

Once code lives in a tree named by its digest, "which code runs in production" stops being a deployment question and becomes an authorization one. A binding record says which tree an agent runs. A generic host reads the binding, materialises exactly that version, runs it in the jail, and claims work as the agent the code belongs to. The code inside gets a channel to propose actions and no credential of its own, so it cannot lie about who it is, and the host stamps what it touched where the code cannot reach.

Promotion is then a grant rotation pinned to a digest: the permission that lets production work be claimed carries the digest it applies to: authorizing the work and authorizing the code become one record.

what is prod running, answered from the enforcement path
$ radia promote t1:07b3e5c918… --tier prod --pin agent:scraper:take,ack
$ radia pins agent:scraper --tier prod
agent:scraper on 'prod': t1:07b3e5c918…

The answer comes from the same records that do the refusing, so it cannot disagree with what is actually enforced the way a deploy log can. A binding that names a tree the grant does not pin is refused rather than run. Rolling back is the same verb pointed at the previous digest, and stopping an agent is a record write; both leave the audit trail everything else does. The founding use case for all of this is model-written code over data it must not exfiltrate, which is why the pieces compose the way they do: the jail bounds what the code can reach, the binding bounds which code runs, and the grant bounds what its output may claim to be.

Data gets in the same governed way it gets out. The code cannot fetch its input, because the jail has no network and the channel out carries no bytes, so the binding declares which fields of a claimed request name stored payloads, and the host lays those bytes into the run's directory before the code starts. The fetch happens under the agent's permission, not the host's: a request naming a payload its handler may not read fails as a refusal instead of smuggling data past the grants. And everything the run produces lists that input as a parent, which carries its labels along.

All of this composes into a worked system in the analysis example: its stages are promoted trees run by one host, pinned on both the claim and the result, and the pipeline's own shape is a registry a new stage joins by deployment alone. The pipeline →

Getting it out

Eventually a person has to see the thing. Two exits exist, and they answer different questions.

Look at it

A multi-file page cannot be viewed one file at a time, because the browser will go looking for the stylesheet. So a short-lived link is minted over the whole tree at once, as a path to artifact index, and served from an isolated origin. The runtime never learns what a workspace is: it was taught to serve an index somebody hands it, and the extension computes that index from a manifest.

Path traversal is structurally absent here, not checked for: the requested path is matched against a fixed index, so there is no filesystem to escape and the index is the allowlist. Every artifact is authorized once when the link is minted; the served URL needs no credential, and a link cannot outlive the permission that created it.

Hand it to git

radia workspace-git
$ radia workspace-git landing-page --dir /tmp/landing.git
landing-page: 7 versions, 34 objects -> /tmp/landing.git
$ git clone /tmp/landing.git && cd landing && git log --oneline
9c1e4a2 attempt 7: fix the header overlap
04b7f30 attempt 6: add the illustration
…

Or serve them, and hand somebody a URL instead of a directory:

radia git-serve
$ radia git-serve
git server on http://127.0.0.1:7790  (reading http://127.0.0.1:7788)

$ git clone http://you:<token>@127.0.0.1:7790/landing-page.git

That is a read of the space wearing a familiar shape, and it runs as you: the password is a credential that can mint a session and do nothing else, so the clone sees exactly the trees you could see and revoking it stops the next fetch. Push is refused with the reason rather than a 404, because pushing is the one direction this does not go.

A real repository, with real objects, that a real git clone reads. No git binary is involved in making it and no dependency was added: hashing and compression are both already in the platform. Each manifest version becomes a commit, the chain of versions becomes the parent chain, and every commit carries trailers leading back to the record it came from.

Export only. There is no import, for two reasons. Git hashes with SHA-1, and chosen-prefix collisions have been practical since 2017, so adopting its object identity would put SHA-1 into the chain that attestations rest on. And git history is rewritable by design, where records are not. Borrow the shape and emit the format; the storage stays Radia's.

What this buys that git does not

Anyone who has purged a leaked credential from a repository knows what it costs: every downstream hash changes, every fork force-pushes, every clone is invalidated, signed tags die. Here a file is an artifact, so one payload can be destroyed while the tree digest still verifies and the history still reads. The blast radius is gone.

And the guarantee is narrower than it sounds; here it is in full. The manifest keeps the path and the hash of the erased file, in a record body that has no erasure path of its own. So credentials/prod-db.txt outlives its own contents, and anyone holding a candidate secret can hash it and confirm that exact value was in that tree. A destroyed build output or document is gone in every practical sense. A destroyed credential is unreadable and still confirmable, and its filename is plaintext forever. What this removes is the blast radius, not the disclosure.

Past that: every file version is attributable to a specific run, the dependency set is inside the record rather than claimed by a lockfile, a grant can scope which workspace an agent may touch at all, and labels track whether a file descends from something untrusted. Branch protection has been approximating that last set for years, and a git hook dies to --no-verify.

What it does not buy: incremental builds, editor feedback, merge, blame. Git does the storage model better and has thirty years of tooling around it. This is not a better git. It is a working tree whose every state is a record the runtime can authorize, attest and erase.
