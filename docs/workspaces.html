Where the work meets the world

Records are a fine way for agents to talk to each other. They are a poor way to hand a three-file website to a person, or to run a program that expects a directory. A workspace is the seam: a multi-file tree an agent can write, run, look at and export as a real git repository. None of it is in the runtime.

An agent that writes code needs somewhere to put it

A single-file evaluator gets you further than you would expect and then stops dead. Real work is a project: write a few files, run the thing, read the error, fix one line, run it again. The loop is not the hard part. The missing part is somewhere for the program to live between iterations.

That is a gap in what agents can reach, not in the coordination model underneath. A round trip through the space costs about thirty milliseconds and a sandbox start about twenty-seven, against a model turn of one to ten seconds. Routing this loop through records costs roughly one percent of an iteration, so the medium was never the constraint.

It is a convention, not a feature of the runtime

This is the part worth being pedantic about, because it is the whole reason the design stays small. Radia has no idea what a file is. It has no idea what a path, a file mode or a directory is. Nothing in the runtime knows the word workspace.

A workspace is a record whose body happens to list files, plus one artifact per file, plus a projection that says which version is current. Every one of those is a primitive that already existed for other reasons. The convention lives one tier out, in a library that talks to the space through the same public API your own code would use.

The dependency rule is enforced rather than encouraged: a test greps for it, and an extension that reached into the runtime would fail the build. That direction is what keeps the runtime from slowly growing opinions about filesystems, and it is why exporting a workspace to git is an ordinary client command instead of a feature of the server.

Two things here are specified, not merely implemented. The tree digest and the path validator cross a trust boundary: a verdict about a tree is comparable across languages only if every implementation hashes it identically, and a path rule that differs between implementations is a hole rather than an inconsistency. Both ship with a conformance suite that any implementation in any language has to pass.

What a tree actually is

One record holds the manifest: a name, a tree digest, the version it was based on, and a list of files. Each entry is a path, a mode, a content hash and the artifact holding the bytes.

a workspace record
{ "name": "landing-page",
  "treeDigest": "t1:9f2c...ade1",
  "basedOn": "01JB2Q7X4KJ8ZN0R5V3M9WPHTC",
  "files": [
    { "path": "index.html", "mode": "100644", "digest": "sha256:4b1e...", "artifactId": "01JB2..." },
    { "path": "style.css",  "mode": "100644", "digest": "sha256:c70a...", "artifactId": "01JB2..." },
    { "path": "cat.png",    "mode": "100644", "digest": "sha256:8ee3...", "artifactId": "01JB2..." }
  ] }

Editing the tree writes a new manifest that points at the version before it, so history is a chain of records rather than a mutable directory. Bytes are shared by content, so changing one character in one file stores one file, not a tree. Two agents editing the same base produce two successors and you can see that they diverged, which beats one of them quietly winning.

A file does not have to be written to be added. An image the agent generated earlier is already an artifact, so attaching it to a tree moves no bytes at all: the manifest points at what is already there, and the artifact becomes a data parent of the tree, so whatever labels it carries follow it in.

radia workspaces
NAME          FILES  VERSIONS  TREE            OWNER
landing-page      3         7  t1:9f2cade1a4…  human:alice
scraper           9        22  t1:07b3e5c918…  human:alice

Paths are validated on the way in rather than on the way out, which is the part that sounds boring and is not. There is no filesystem inside the space, so a path is just a string in a record until something materialises it, and every rule about what a path may contain gets applied at the moment it is written. Materialising the tree revalidates anyway, and checks that each resolved file really landed inside the directory it was supposed to.

Running what is in it

A tree is only interesting if something can execute it, and executing model-written code is a question about isolation rather than about languages. Two jails ship. One runs JavaScript in a subprocess with no permissions at all, safe by the absence of every flag. The other runs any interpreter inside bubblewrap, safe by the presence of the right ones.

Those are not equivalent, and the difference is not something to paper over in a sentence on a web page. So a jail is a record: it states what it actually guarantees, an operator declares it, and the worker probes it before serving anything. A bubblewrap jail missing one flag can reach the network while its record claims it cannot, so nothing is advertised on the strength of a claim. Only on a passed probe.

Which means the answer to "what can this space run" is discovered rather than configured. A runner publishes run_javascript or run_python only where its backend probed clean, so a language the host cannot isolate is simply absent from the tool list instead of failing after a turn has already committed to it.

The process that runs the code holds no credential. The worker that spawns jails can start two specific binaries and reach the space, and nothing else. The child it spawns gets no permissions and no token, so compromising the dangerous half yields a process that can print bytes to its parent.

Getting it out

Eventually a person has to see the thing. Two exits exist, and they answer different questions.

Look at it

A multi-file page cannot be viewed one file at a time, because the browser will go looking for the stylesheet. So a short-lived link is minted over the whole tree at once, as a path to artifact index, and served from an isolated origin. The runtime never learns what a workspace is: it was taught to serve an index somebody hands it, and the extension computes that index from a manifest.

Path traversal is structurally absent here, which is a nicer property than a careful check. The requested path is matched against a fixed index, so there is no filesystem to escape and the index is the allowlist. Every artifact is authorized once when the link is minted, so the served URL needs no credential and a link cannot outlive the permission that created it.

Hand it to git

radia workspace-git
$ radia workspace-git landing-page --dir /tmp/landing.git
landing-page: 7 versions, 34 objects -> /tmp/landing.git
$ git clone /tmp/landing.git && cd landing && git log --oneline
9c1e4a2 attempt 7: fix the header overlap
04b7f30 attempt 6: add the illustration
…

Or serve them, so the URL is the thing you hand somebody rather than a directory:

radia git-serve
$ radia git-serve
git server on http://127.0.0.1:7790  (reading http://127.0.0.1:7788)

$ git clone http://you:<token>@127.0.0.1:7790/landing-page.git

That is a read of the space wearing a familiar shape, and it runs as you: the password is a credential that can mint a session and do nothing else, so the clone sees exactly the trees you could see and revoking it stops the next fetch. Push is refused with the reason rather than a 404, because pushing is the one direction this does not go.

A real repository, with real objects, that a real git clone reads. No git binary is involved in making it and no dependency was added: hashing and compression are both already in the platform. Each manifest version becomes a commit, the chain of versions becomes the parent chain, and every commit carries trailers leading back to the record it came from.

Export only. There is no import, and that is a decision rather than a gap. Git hashes with SHA-1, and chosen-prefix collisions have been practical since 2017, so adopting its object identity would put SHA-1 into the chain that attestations rest on. Git history is also rewritable by design, and records are not. Borrow the shape, emit the format, refuse the storage.

What this buys that git does not

Start with the one that is a genuine operational win. Anyone who has purged a leaked credential from a repository knows what it costs: every downstream hash changes, every fork force-pushes, every clone is invalidated, signed tags die. Here a file is an artifact, so one payload can be destroyed while the tree digest still verifies and the history still reads. The blast radius is gone.

And the guarantee is narrower than it sounds, so here it is in full. The manifest keeps the path and the hash of the erased file, in a record body that has no erasure path of its own. So credentials/prod-db.txt outlives its own contents, and anyone holding a candidate secret can hash it and confirm that exact value was in that tree. A destroyed build output or document is gone in every practical sense. A destroyed credential is unreadable and still confirmable, and its filename is plaintext forever. What this removes is the blast radius, not the disclosure.

Past that: every file version is attributable to a specific run, the dependency set is inside the record rather than claimed by a lockfile, a grant can scope which workspace an agent may touch at all, and labels track whether a file descends from something untrusted. Branch protection has been approximating that last set for years, and a git hook dies to --no-verify.

What it does not buy: incremental builds, editor feedback, merge, blame. Git does the storage model better and has thirty years of tooling around it. This is not a better git. It is a working tree whose every state is a record the runtime can authorize, attest and erase.
