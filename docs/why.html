Why not just use X?

Fair question, and there are several good candidates. Most of them do one of these two jobs well. Almost none of them do both. Below is where each one is genuinely the better answer, and where it runs out.

The short answer

Two things are unusual here. Routing is stored data you can look at and refuse, rather than a name in somebody's code. And permission is granted one record at a time, based on what the record contains, rather than per queue or per namespace.

Take almost any comparable system and you will find it has one of these, or neither. That is the whole claim, and it is easy to check.

How work is routedHow access is grantedWhat a result is
Radia a stored description you can query per record, by its contents a record others can pick up
Temporal function name on a queue per namespace an opaque value in a history
NATS, RabbitMQ, Kafka a key the sender chose per topic a message, gone once handled
DBOS function name everything shares one identity a durable step
LangGraph, CrewAI edges you wrote in code none a value in memory

Why not a queue, or a topic exchange?

This is usually the first thing people say, and it is the strongest challenge on the list. RabbitMQ, NATS and Kafka route by content in some sense, they are everywhere, and they are very good. If your problem is moving messages between services, use one of them.

The difference shows up when the answer matters as much as the request. When a consumer acknowledges a message, it is gone. Whatever it produced is now somewhere else, in a database you set up for the purpose, and getting the two back together is your job.

Two smaller differences. You cannot ask a broker who would receive a message if you sent it, because the bindings live in its configuration rather than in something you can query. And a topic permission covers a topic; there is no way to say that this agent may have this particular message and not that one.

None of that means you should stop using a queue. Bridging one into a space is a normal thing to build, and plenty of systems want both.

Why not Temporal?

If what you need is durable execution, use Temporal. It has a decade of production behind it, SDKs in every language you are likely to want, a managed cloud, and a long tail of hard problems already solved. Radia does not compete with it and would lose.

What Temporal does is remember how far a workflow got, so it can pick up after a crash. What it does not do is tell you which worker should handle a piece of work based on what that work contains, or let you refuse a payload to a step. Activities are invoked by name, and the payload is a blob it passes along without opening.

For agents that turns into a specific gap. The routing decision moves into the model, where nobody can inspect it beforehand or deny it as it happens, and there is nowhere in the design to ask whether this particular document should reach this particular step.

These stack, and that is the more interesting option. A Temporal workflow can have activities that are Radia participants, or a space can be the exchange between workflows owned by teams that cannot edit each other's code. Temporal keeps the durable call stack, which is deliberately not something Radia tries to have.

Why not LangGraph or CrewAI?

Because in a framework the tool list is the program. Agents and tools are objects you construct and wire, so the shape of the system is a thing you wrote down, and changing it means editing and redeploying.

That is genuinely fine for a lot of work, and it is faster to start. It gets uncomfortable at the point where several teams own several agents, or where you want to add a capability without touching the thing that will use it, or where everything running in one process with one set of credentials becomes a problem you have to explain to somebody.

Radia's chat example is the demonstration: its command loop contains no tool list, no model name and no routing. It learns what tools exist by reading records, and starting another worker changes what the assistant can do without touching the assistant.

The cost is real. A tool call here is a database write, a claim and an answer, where a framework does a function call. You are buying history, retries, per-record permission and an audit trail. For a fast local tool that nobody will ever need to audit, that is a bad deal, and you should use the function call.

What about DBOS?

DBOS is the closest thing to a sibling. It makes the same underlying bets: Postgres as the one source of truth, stateless processes above it, durability recorded per operation rather than as a stream of events to replay. Its published performance numbers are the best evidence available for what this shape of architecture can do, and where it slows down is contention on the front of a queue, which is exactly the same wall a single-winner claim hits.

The difference is not speed. In DBOS every process talks to Postgres directly, holding database credentials, and routing is by function name. Radia puts one server in the middle so that mutually distrusting agents can share a space, and pays for it with a network hop and a permission check on every operation. Take those two things away and you would have something very like DBOS.

Do not read those numbers as headroom here. They come from a saturation test on a tuned database with processes writing to it directly. Every operation here also matches a pattern, ranks candidates, checks permission and appends to a log, behind an HTTP request. Same wall, unknown distance from it.

Is there any evidence this works better?

Some, and it is worth being precise about how much.

A 2025 paper by Salemi and colleagues built a system where a coordinating agent posts requests to a shared board and other agents volunteer for the ones they can handle, so the coordinator never needs to know what any of them are good at. That is the same idea as claiming by description. On three data-discovery benchmarks it improved end-to-end success by 13 to 57 percent over strong baselines.

A second paper the same year reports competitive results at lower token cost, beating both single-agent prompting and fixed multi-agent setups.

Both are encouraging, both are specific to their workloads, and neither was run on this system. There is no benchmark of Radia itself yet. So the honest position is that the idea has independent support and the implementation does not.

The bet underneath all of this

This style of coordination is old, and it keeps losing. Systems that let components find each other by description have existed since the 1980s and never took over. Something simpler always won: a framework that let you write the sequence out as ordinary code with a call stack you could step through.

The reason seems to be that people think in stories. A workflow you can read top to bottom is easier to hold in your head than a set of independent parts whose behaviour only appears when you run them together, even when the second one is more flexible.

So the bet is this: an LLM agent may not have that problem. It reads what is available right now, matches on what is in front of it, and does not mind that the arrangement was different an hour ago. That is precisely what these systems asked of people and mostly did not get.

It could be wrong, and there are two things that would show it. Somebody builds a second implementation and puts a routing table in it anyway. Or applications keep hardcoding the things they were supposed to discover. On that second one there is already evidence pointing the wrong way: this project's own chat example did it four times and was corrected each time in review. Those were mistakes by a person writing the code rather than by an agent at runtime, so they do not settle it. However, they are the closest thing to evidence anyone has right now, and pretending otherwise would be silly.
