Why not X

Take the nearest system in each family and remove two cells, trust and routing. What is left over is this. Three different families, the same two things missing: routing that is stored data a policy can refuse, and authorization at the granularity of one record.

1. The gap, stated as a subtraction

A feature conjunction is defensible by construction. This is not.

RoutingAuthorizationResults are
Radia stored pattern, queryable per record, by body records others match
Temporal function name on a queue per namespace opaque payloads in a history
NATS, RabbitMQ, Kafka key the publisher chose per topic or subject messages, gone on ack
DBOS function name one trust domain durable steps
LangGraph, CrewAI edges in your code none values in a process

This is falsifiable in a way a six-way feature list is not. Fill those two cells in any row and the claim is gone.

2. Why not a broker with a topic exchange

The first question, and it arrives before the Temporal one.

Subject wildcards, headers exchanges, JMS selectors and Kafka with a stream processor all route by content in some sense, all are deployed everywhere, and none of them lost. Four differences, in the order they matter.

  • A subscription is not data. Bindings live in broker configuration, so you cannot ask a broker who would receive a message before publishing it. Interests are records here, and there is an endpoint that answers exactly that against a draft.
  • An ACL scopes a namespace; a grant scopes a record. A topic ACL cannot express "this agent may claim this payload but not that one".
  • Competitive claiming with fencing. A queue gives at-most-one consumer. A lease gives one winner, a renewable hold, and a fenced epoch, so a slow worker's late write is refused rather than accepted after somebody else redid the work.

None of that makes a broker the wrong tool for transporting messages. It makes it the wrong tool for a shared knowledge store that also has to authorize per payload. A bridge writing records from a subject or a topic is a normal thing to build.

3. Why not Temporal

Radia does not compete on durability, and a pitch that leads with it loses.

Temporal is the incumbent for durable execution, with a decade of production hardening, many language SDKs and a managed cloud. Any pitch that opens with durable resumable workflows invites "so why not just use Temporal, which my platform team already runs", and that is a comparison to lose. The models do not overlap in three places.

  • Content routing versus addressed dispatch. Temporal invokes an activity by type name on a named queue, so adding a capability edits the calling workflow. Its agent story puts the routing choice inside the model, where it cannot be inspected or denied.
  • Record-scoped authority versus namespace-scoped. Within a namespace a workflow may touch any activity on its queues, and payloads are opaque with no per-record classification.
  • A data plane versus an execution log. Temporal caps payload and history size and tells you to keep large data out. The history is an execution log, not a knowledge store; "what does the system currently know about X" needs an external store.
Compose, do not compete. Temporal workflows whose activities are Radia participants, or Radia as the exchange between workflows owned by teams that cannot edit each other's code. The defensible sentence is "the classification and containment layer that durable-execution engines do not have", never "a better Temporal".

4. Why not an agent framework

In a framework, the tool list is the program.

LangGraph, CrewAI and AutoGen bind tools and agents as objects at construction. The graph is code, so adding a capability is a deploy, and the whole arrangement lives in one process with one set of credentials.

Here a worker publishes what it serves as a record. The agent watches those records and builds its tool list from them, so starting a worker adds a tool with no change to the agent, its prompt, or anything else. The chat example does this literally: its REPL contains no tool table, no model name and no routing.

The cost is real and worth saying. A tool call here is a database write, a claim and an ack, against a function call in a framework. That buys lineage, attempts, classification and audit. For a fast local tool nobody will ever audit, it is the wrong trade.

5. DBOS, the closest living relative

The same three bets, and two cells of difference.

DBOS makes the same wagers: Postgres as the sole arbiter, stateless processes over it, durable facts at operation granularity rather than an event-sourced history. Its published numbers are the best available evidence for this architecture's ceiling, and the bottleneck it hits is lock contention at the head of a queue, which is the same wall as a single-winner claim gate and as contended take in JavaSpaces thirty years ago.

The divergence is trust topology rather than performance. In DBOS every app process is a direct Postgres client, one trust domain holding database credentials, and routing is static. Radia inserts exactly one server to create a boundary between many mutually untrusting principals, and pays an HTTP hop plus authorization per operation for it.

Do not read those numbers as headroom here. They come from a saturation test on a tuned Postgres with app processes writing directly, while every operation here also compiles a pattern, ranks candidates, authorizes and appends an event behind an HTTP hop. Same wall, same shape, unknown distance from it.

6. The evidence, and its limit

Two papers, neither run on Radia.

Salemi et al. 2025 built a system where a central agent posts requests to a shared blackboard and subordinate agents volunteer according to their capabilities, which removes the need for the coordinator to know each agent's expertise. That is content-routed claiming by advertised capability, tested independently: 13 to 57 percent relative gains in end-to-end success on three data-discovery benchmarks, and up to 9 percent on data-discovery F1.

Han and Zhang 2025 report competitive performance at lower token cost, beating chain-of-thought and static multi-agent baselines while cutting tokens.

Both are encouraging and workload-specific. Neither was run on this system, and there is no internal benchmark yet. Until one exists, the differentiator rests on other people's experiments on other people's systems.

7. The wager, and what would settle it

Choreography keeps losing because people think in narratives.

Both ancestries here were technically sound and both lost to orchestration. Spring beat OSGi by offering the service registry's benefits with the dynamism removed. Declarative Services succeeded by hiding it. Temporal and DBOS thrive today on writing coordination as ordinary imperative code with a call stack.

So the bet is specific: LLM agents may be the first population that does not carry the handicap. An agent reads the capabilities present now, matches on what is in front of it, and tolerates topology changing between turns. That is what OSGi asked of humans and mostly did not get.

Two observations would falsify it: a second implementer who builds a routing table anyway, and an application that needs another entry on the list of things an agent hardcoded when it should have discovered them. That list already has four entries, all from this project's own chat example, and all caught in review rather than by the substrate. They are authoring failures by a human rather than an agent failing at runtime, so they do not settle it. However, a project that treats other people's failures as a mortality table has to carry its own.
