What the system can tell you about itself

Nothing here declares how work flows, so there is no diagram to open. That is the design working, and it is also a bill that comes due the first time somebody asks what this system does. Here is how it gets paid.

Where is the workflow?

It is the first question every newcomer asks, and the honest answer is that there is not one. A worker says what shape of record it handles, the space matches, and the system's behaviour is whatever those independent declarations add up to while it runs. No file describes it.

The tempting fix is to ask each agent to declare its place in a pipeline. That is a routing table with extra steps, and the whole point of the substrate is not to have one. So the shape is worked out backwards instead, from what actually happened: take every group of records that are causally connected, reduce each group to the sequence of steps it went through, and count how often each sequence recurs.

radia flows
 180x  100%  n= 2     1.3s  a request → a reply
 104x  100%  n= 7     7.6s  conversation ⇒ request → request + message → reply
  73x  100%  n= 4   810ms  conversation ⇒ tool call → message + result
   3x  100%  n=10   229ms  job ⇒ pieces ×4-7 → results ×4-7 → summary

3905 records over 14 kinds, 218 subgraphs, 2 cut as hubs (--hub-degree 0 to leave them whole)

The columns are how often the shape happened, how often it finished, how many records were involved, and how long it took. The last line is the part that keeps the rest honest.

A shape that starts often and finishes rarely sits next to the ones that work, which is usually the most useful thing on the screen. In a log, a job nobody ever picks up and a job whose worker keeps crashing look identical, and they need opposite fixes. As shapes they are obviously different: one has two steps and never a third, the other has a third that keeps repeating.

A mined diagram looks equally complete whether it is or not. So the incomplete cases are printed rather than left to be inferred: a long-lived record that touches everything is cut out and said to be cut, a group whose parent fell outside the scan is counted as a fragment, and anything that would make the picture partial is reported on the same line as the picture.

Who is listening right now

Mined shapes tell you what the system has done. They cannot tell you what it would do next, because a worker that started a minute ago has no history yet. That is a separate question and it has a separate answer: a run publishes what it is listening for, as a record, so the routing topology is queryable rather than implied.

Which makes a useful thing possible before you commit to anything. Describe a record you are thinking of posting, and ask who would receive it.

POST /v0/ops/dry-run
$ curl -s $SPACE/v0/ops/dry-run -H "$AUTH" \
    -d '{"kind":"document","body":{"type":"pdf","classification":"confidential"}}'

{ "kind": "document",
  "interests": [
    { "run": "run:01JB2Q3D7M", "agent": "agent:ocr", "match": {"type":"pdf"} }
  ] }

One worker would take it, and the summarizer would not, because its grant is scoped away from confidential documents. You learn that without writing the record, which is the difference between a question and an experiment.

When nothing matches, the answer says so and says what that does and does not mean: either nothing is listening for this, or the workers that would are not running. An interest is only live while its run is.

An interest is a declaration, not evidence. A worker publishes one best-effort, so a worker that never published, or has no permission to, is invisible here. That caveat is attached to every answer that depends on it rather than documented once and forgotten.

What is stuck, and why

An operator asks a narrower question, and wants it answered in one command. Work that has been sitting unclaimed for too long is the usual complaint, and the count on its own is close to useless, because two completely different faults produce the same number.

radia doctor
available=1204  leased=8  consumed=39112  dead_letter=3
dead-letter: 3
stuck leases: 2 (expired but still held)
stale available: 47 (11 orphaned: nothing is listening; 36 starving: a listener is not claiming)
  orphaned invoice 01JB2Q7X4KJ8ZN0R5V3M9WPHTC
  an interest is a worker's own declaration and publishing one is best-effort, so
  'orphaned' means no live interest MATCHES, not that nothing is listening.
event chain: 39112 links, UNSIGNED (detects corruption, not a rewrite; set RADIA_SEAL_KEY)

Orphaned means nothing is listening for this shape of record, and you fix it by starting a worker or correcting a pattern. Starving means somebody is listening and not claiming, and you fix it by looking at that worker. A single number for both leaves an operator to guess which one they have, which is where the time goes.

The same vocabulary does the repair. The selector that diagnoses is the selector that remediates, so finding expired leases and releasing them are one expression rather than a report followed by a loop over ids.

What happened, exactly

Underneath all of this is an event log written in the same transaction as the change it records, so there is no window in which a thing happened and the log disagrees. Every claim, every ack, every write.

Records point at the records they came from, which makes two questions cheap in opposite directions. Ask a record for its ancestors and you get the chain that produced it. Ask it for its children and you get everything derived from it, which is how a conversation lists its own messages without a table joining them.

radia lineage
● 01JB2Q9F3H  summary
  └ 01JB2Q7X4K  document
    └ 01JB2Q1A8P  upload_batch

Lineage is data, never authority. A record derived from a privileged one inherits nothing from it. Permission travels a separate chain, derived from the claimed lease, and the two are kept apart on purpose: the alternative is a system where reading a secret quietly makes you trusted.

If your team already lives in a tracing tool, the same picture exports as OpenTelemetry: radia otlp --to http://localhost:4318 --follow streams threads into Jaeger or Tempo as traces, with each work attempt as a span, the claiming agent as the service, and the labels and delegation chain as searchable attributes. Nothing is installed on either side; it is one command talking plain OTLP over HTTP.

Whether to believe any of it

All of the above is computed from the log, so the log had better be intact. Finalized events are sealed into a hash chain, each link covering the one before it, and the result is checkable in one command.

radia integrity
chain OK: 39112 of 39112 links verified, signed
head 39112 8f3c1d0ba2e47591…
14+ events not yet sealed (sealing follows the finality watermark)

Sealing waits for the point past which no earlier event can still arrive, so the chain never covers a gap that later fills in. Events above that line are real and simply not sealed yet.

Unsigned, this detects corruption and careless edits, not a rewrite. Anyone who can edit the log can recompute the hashes. Signing the chain under a key held outside the database is what makes an edit detectable, and until that key is set the tool says so on every run rather than letting an unsigned chain be quoted as tamper detection.

There is one more thing this catches that nothing else would. A payload can be destroyed on request, which the substrate supports precisely because records are otherwise immutable. But destroying the copy here does not make those bytes unstorable: anyone still holding them can write them again, they land at the same content address, and every record pointing at them reads once more. Refusing to store them a second time is not the fix and was tried, because it poisons that address for everyone. So the state is reported instead, as an erasure that no longer holds. Hiding it is the only unrecoverable option.

The part that is still missing

A newcomer's real question is closer to "show me" than "list the shapes", and the console answers that better than any of these commands: the Space tab streams live activity and the Flows tab renders mined shapes with the record ids that are the evidence behind each one. What does not exist yet is a view of standing interest, live, next to the traffic it explains.
