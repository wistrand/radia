Examples

They ship with the source, and all but the chat need no API key at all, which means you can watch the whole thing work before deciding whether you believe any of this.

Start here: a pipeline with no wiring in it

Run deno task demo and four small programs come up. One splits a job into pieces. Two do the work, each handling only the kind of piece it knows how to do. The fourth waits until the results are in and writes a summary.

The interesting part is what you will not find in the source. None of the four imports another. There is no configuration listing them. The one that splits the job has no idea whether anyone is out there to do the pieces, and the one that writes the summary never learns who produced the results it read.

Open the console while it runs and you can watch records appear and change colour as they are claimed and answered.

A real agent, with everything as records

The chat example is a command-line assistant, and it is where this design gets stress-tested. A fleet of separate processes, with separate credentials and separate operating system permissions. The one that reads files cannot reach the network. The one that runs code holds no credential at all.

The program you type into makes no external calls whatsoever. It writes a record saying a question was asked, and reads the records that come back.

one turn of conversation, as it appears in the space
a message        // what you typed
a request        // no model named: the chat does not choose one
  a request      // a router picked a model and asked again
  some chunks    // the reply, streaming in
  a reply
a tool call      // whichever worker offers that tool claims it
  some progress
  a tool result
  a verdict      // written by the runner, not by the model
a reply          // carrying the provider's own token and dollar figures

Because the conversation is records rather than memory, it survives a restart, you can resume it by name, and anyone with permission can inspect it. The verdict is the line worth pausing on: when the assistant runs code and claims it worked, something other than the assistant checks and records the answer. The assistant has no permission to write that record.

The assistant's tool list is not configured anywhere either. Each tool worker advertises what it offers as a record, description included, and the assistant watches for those records to build the list it shows the model. Start a new worker mid-conversation and the next turn has its tool. The client knows the names of nothing: not the tools, not the models, not the record kinds beyond its own, which is the discipline that keeps a capability an act of deployment rather than a code change.

The reply carries what it cost, in the provider's own numbers, and those fields are declared sortable, so "which call used the most tokens" is a query with an answer rather than a guess. Model choice reads the same way in the other direction: say a tier's name and the router obeys, and a bare "continue" keeps the tier the last turn ran on, because eight characters of text say nothing about how hard the work is.

A conversation can also be sealed end to end. Start one with --encrypt and the prose of every message, tool argument and tool output is ciphertext to everyone but its owner, while the records still route, because nothing ever matched on prose. The keys live in destroyable payloads, so erasing the conversation means destroying its key, and the records, their lineage and the audit chain all survive the erasure. The design was forced rather than invented: every wrong place to keep the keys, a shared fleet secret, the conversation record itself, an ordinary record body, broke a rule the runtime already had, until the one shape that satisfied them all was left standing.

A shelf of test suites, none of which needs a model. Because a tool call is a record and assembling the context is a plain function, the tests drive the real thing with no API key. Most bugs in this project have surfaced here first.

A data pipeline where re-running is not a mechanism

The analysis example is a web app: sign in, upload a CSV, watch each stage run, follow any record into the console. What makes it worth reading is what it does not have — no replay verb, no invalidation pass, no "mark stale" flag. The app itself holds no credential either: it relays the browser's own token, so the space applies the signed-in person's grants and the app cannot exceed them or leak what it never held.

Work is identified by its content: which dataset, the digest of the input, the digest of the code that will run. All three are indexed, so "has this already been computed" is one query. Each stage's output is an artifact, so its content digest is the next stage's input digest. Change an analysis and that stage re-runs along with everything after it, because those keys now miss; change nothing and nothing re-runs, however often the planner executes.

The code that runs is a record too. Each stage lives in a workspace tree named by its digest, and that digest is the same value the work request carries and a promotion grant pins. So a stage can only ever be handed work naming its promoted tree, and a result claiming any other digest is refused at the moment it is written. The question every cached answer rests on, which code produced this, went from a field a worker reported to a fact the grant table enforces in both directions. The code itself runs in a jail holding no credential: a generic host fetches its input under the stage's own permission, and stamps its output with the person the work was for, so that person's scope reaches bytes an agent computed on their behalf.

And the pipeline's shape is itself data. The list of stages is a registry the planner and the page both read, so adding a stage is a deployment: store the tree, declare where it goes in the order, promote its digest, bind it. The example's own test does exactly that, deploying a fourth stage into the live pipeline while it runs, and only the new work computes; nothing restarts and no process that was already running learns anything. A tree authored anywhere qualifies, including one an agent wrote in conversation, because deployment names a digest and nothing else.

The one thing the runtime cannot decide for you is which work is stale, and that is the whole of planner.ts. Deciding it depends on what you consider an input. Everything else — the DAG, the routing, the leases, the audit, and now which code may answer — is already there. That split is the property to look for in any coordination runtime: the part left to you should be the part only you could know.

Watching it happen

Start a space and there is a web console at the same address. It is built on the public API, so it can only show you what any other client could ask for.

Overview ranks what deserves attention, and every finding links to the records it rests on. Feed is a live view of everything happening. Graph draws how records connect, a conversation and its messages, a job and its pieces, with a waterfall view that reads like a trace: time as the axis, so you can see which tool the seconds went to. Kinds draws who is listening for what right now, mined from live declarations rather than configuration. Space arranges every record by what it is rather than by what it links to, which is a surprisingly good way to spot a fleet doing something odd. Flows renders the recurring shapes with their evidence. Auth shows who exists and what they may do.

Whatever you are looking at is in the address bar, so you can send someone a link to it, and it survives your session expiring while you are in the middle of looking at something.

Finding the shape after the fact

Here is a problem this design creates for itself. If nothing declares how work flows, there is no diagram to look at. New people ask where the workflow is, and the honest answer is that there is not one.

So it gets worked out from what happened. Take everything that is causally connected, reduce it to the sequence of steps involved, and count how often each shape occurs.

radia flows
 180x  100%  n= 2     1.3s  a request → a reply
 104x  100%  n= 7     7.6s  conversation ⇒ request → request + message → reply
  73x  100%  n= 4   810ms  conversation ⇒ tool call → message + result
   3x  100%  n=10   229ms  job → pieces ×4-7 → results ×4-7 → summary

The bottom line is the pipeline from earlier, found without anybody describing it. The columns are how often it happened, how often it finished, how many records were involved and how long it took.

Shapes that start and rarely finish show up next to the ones that work, which is usually the most useful thing on the screen. A job nobody ever picks up and a job whose worker keeps crashing look identical in a log, and they need completely different fixes.
