Authorization

When an LLM writes the plan, the routing decision moves inside the model, where you cannot inspect it or deny it. Grants move it back out. An agent claims work by matching a stored pattern, a grant scopes what it may claim, and the check runs inside the claim transaction rather than in the agent.

1. Why this belongs in the substrate

Two of nine tuple-space systems ever had access control.

The COORDINATION 2016 survey benchmarked nine implementations of this idea. Two had any access control at all. The lineage treated security as an optional feature, which is most of why it stayed a research paradigm.

A shared space between agents that do not trust each other is exactly where that gap bites. An agent's plan is written by a model, so "which worker gets this" is a decision no reviewer sees. Putting the decision in records makes it inspectable before the fact and refusable during it.

2. A grant is a record, not a config table

Assigned, never self-declared.

An operator writes a grant record; the runtime discovers it by query. Authorization state gets the same immutability, event-log visibility and watchability as everything else, and revoking is a successor record carrying retired: true, so the audit trail survives the revocation.

grant
{ "principal": "agent:summarizer",
  "kind": "document",
  "operations": ["take", "query", "read_one"] }

Grants are kind-scoped and never wildcard. A capability a worker claims to have is descriptive; it authorizes nothing. The two are deliberately different records, because the failure mode of conflating them is an agent that grants itself what it says it can do.

3. Pattern scoping: the grant is ANDed into the request

Not a filter applied afterwards.

Scoping works on writes too: a pattern-scoped put grant requires the record's body to satisfy the pattern. And scope: {createdBy: "self"} restricts a principal to its own records, which is how one person's session on a shared space cannot read another's.

4. The bootstrap chain

Short-lived run tokens, from a definition an operator wrote.

A person gets a session through the same chain. human: is a namespace, not a privilege: a logged-in person is an ordinary principal unless the space names them an operator.

5. Delegation is derived from the lease, never from parents

Provenance is not authority.

When a worker acks a result, the runtime records the authority chain the work flowed under, built from the lease it actually claimed. Data parents contribute nothing to it. That separation is what stops an agent from deriving a record from a privileged one and inheriting its reach.

6. Classification labels a grant can bar

Three labels, all barriers, and clearing one needs privilege.

Records carry labels drawn from a closed set: file, net, foreign. They union along data parents, so a result computed from a file read carries file. Raising a label is monotone, which means a client can add one without being trusted and can never subtract one.

The barrier is applied inside the claim, not by the worker asking for it. A worker cannot decline to be restricted, which is the difference between a control and a convention.

This started as a single boolean and had to be replaced. Measured on a real conversation, after one tool call every record carried the bit, so it barred nothing. A label exists only where a lineage walk would be too slow to run, since provenance is already in the log.

7. Checking what a principal can actually do

Every grant bug so far was a promise that did not match the enforcement.

the fold over a principal's grants, from the enforcement itself
$ radia permissions agent:summarizer
KIND       OPERATIONS          SCOPE
document   take, query         classification=public
result     put                 own records only

The same answer is available at GET /v0/ops/permissions and as a tool the chat example's agent can call on itself. Any principal may read its own permissions, including one with no grants at all: that is the caller most likely to need the answer, and gating it left an agent unable to tell an approved grant from a pending one.

8. Known limits

Stated here because the design centre is the wrong place to be vague.

  • The embedded path bypasses grants. Authorization is enforced at the HTTP boundary. A host that embeds the runtime and calls put in-process writes past every grant. Real deployments should talk to the server.
  • No OIDC yet. Identity is the bootstrap chain and nothing else. Federated identity and a hardened single-node deployment mode are both open.
  • No budgets. Per-principal spend limits and trust classification are designed and unbuilt.
  • Record bodies are plaintext. They have to be, because the routing language matches on them. Encryption at rest covers artifact bytes.
