Keeping the confidential one out

Your summarizer sends text to a model hosted by someone else. Most of your documents are fine. Some are not, and you would like that to hold even after somebody writes a careless agent next week. This page is about where that rule lives.

The obvious place to put the rule is the wrong one

The natural instinct is to put the check in the summarizer. Read the classification, and skip anything confidential. It works, and it lasts until the day someone writes a second worker and forgets, or the model decides to be helpful and calls a tool you did not expect it to.

This is worse with agents than it is with ordinary software, because the decision about what to do next is made by a model at runtime. A code reviewer can read a workflow and see which service gets called. Nobody can read a model and see which document it will reach for.

So the rule goes somewhere the agent cannot reach. The document is a record sitting in the space, the worker has to ask for it, and the asking is where the answer is decided.

Permission is a record, like everything else

You give an agent access by writing a grant. It says which principal may do what to which kind of record, and it is stored in the space alongside the documents themselves.

the summarizer may read and claim documents
{ "principal": "agent:summarizer",
  "kind": "document",
  "operations": ["take", "query"] }

Keeping this as a record rather than a configuration file has a few consequences that turn out to matter. You can watch permissions change as they happen. You can ask what somebody could do last month. And taking access away is not a deletion, it is a newer record saying the old one no longer applies, so the trail of who granted what and when survives the revocation.

Grants are always given, never taken. A worker can announce what it is able to do, and that announcement is how other agents discover it, but it grants nothing at all. Those are two different records on purpose, because the alternative is an agent that authorizes itself by claiming to be trustworthy.

Narrowing it down to the contents of the document

The grant above is too broad for our problem: it covers every document. Add a pattern and it covers only the ones whose contents match.

now it is only the public ones
{ "principal": "agent:summarizer",
  "kind": "document",
  "operations": ["take", "query"],
  "pattern": { "classification": "public" } }

When the summarizer asks for work, its request and its grant are combined, and it is served the overlap. Ask for finance documents and you get public finance documents. Ask for confidential ones and you get nothing at all, in exactly the way you would get nothing if none existed.

The same narrowing works on writing. If a worker may only write records tagged with a particular customer, a record tagged with a different one is refused at the door. And a common case has its own shorthand: restrict an agent to records it created itself, which is how two people sharing a space cannot read each other's conversations.

Who a worker is, and for how long

All of this needs the space to know who is asking. Workers do not carry long-lived passwords. An operator defines an agent once, saying what it is called and what it may do. That definition can then mint short-lived tokens, one per running process.

People get credentials the same way. Being a human is not a privilege here: a person logging in is an ordinary principal with ordinary grants, unless the space has specifically been told they are an operator.

Nobody re-authenticates by hand

A short-lived token is only short-lived if something can replace it, and renewing needs a process that is awake to renew: a command you just typed is not, a closed browser tab is not, and a tool that stores a password in a config file never was.

So the definition above is the durable half of the pair, and it is deliberately powerless. It cannot read a record, write one or claim work; the space refuses it for anything except minting a session. That is what makes it safe to keep on disk, and it is what a client presents when its short token lapses, which it does silently and without asking anyone. One revocation ends it, and it is the only thing that does.

This is the same shape OAuth arrived at, with the durable credential unable to act and the acting one unable to last. Nothing here is an access-control decision so much as a decision about what a leak costs: fifteen minutes for the token that can do things, and one command for the one that cannot.

Following data after it has moved

Blocking access to the confidential document handles the direct case. It does not handle the indirect one, which is where these systems usually leak.

Suppose an agent is allowed to read local files. It reads one, and writes a record with what it found. That record is now new, it is not marked confidential, and nothing stops it going anywhere. The sensitive content has escaped by being copied.

So records carry labels that follow the data. There are three of them, and they mean "this came from a file", "this came from the network", and "this came from outside". When a record is derived from another, it inherits the labels of everything it was derived from. A summary of a file read carries the file label whether or not anybody remembered to add it.

Labels only ever get added. Any process can mark its own output as sensitive without being trusted to do so, and no process can remove a mark. Clearing one takes an explicit, privileged action, and it leaves a record of who cleared what.

This started out as a single yes-or-no flag, and had to be replaced. On a real conversation, after one tool call every single record was flagged, so the flag stopped meaning anything and nothing ever refused work because of it. Three specific labels turned out to be useful where one general one was not.

When one agent works on behalf of another

Work usually arrives in chains. Your summarizer produces a summary, which triggers a filing step, which triggers a notification. It would be reasonable to assume the filing step inherits its authority from the summary it is working on.

It does not, and the distinction is deliberate. Authority comes from the job the agent actually claimed, not from the data it happens to be holding. Otherwise an agent could reach for something powerful, name it as an input, and inherit its reach. Reading a document tells you where information came from. It never tells you what the reader is allowed to do.

There is a separate mechanism for the case where a shared worker genuinely does serve many people: it asks for a second, narrower credential, whose reach is the overlap between its own grants and those of the person whose work it claimed. It then holds two, and picks per operation: its own for the things that are its job, the narrow one for anything touching that person's data. The overlap is computed once, when the credential is minted, and it can only ever be smaller than both sides.

Who it is acting for is never something the worker states. It is read from the record it claimed, back through the credential that wrote it, so a chain of workers passing one request along still resolves to the person at the head of it.

Finding out what an agent can actually do

Every permission problem in this project so far has been the same shape: what somebody believed they had granted was not what was being enforced. So there is one command that answers the question from the enforcement side, rather than by reading back the grants you wrote.

what this agent can really do, right now
$ radia permissions agent:summarizer
KIND       OPERATIONS          SCOPE
document   take, query         classification=public
summary    put                 own records only

Agents can ask this about themselves, which is more useful than it sounds. An agent that has just been refused something can find out whether it is waiting on a human to approve a request or whether the approval already happened and it should try again. Asking about anyone else needs the observe power below, or an operator.

Running the space is not one job

There is a second plane of verbs for whoever operates the space: read everything, unstick work, run garbage collection, clear a data-handling flag, destroy a payload. For a while, holding any of that meant holding all of it, plus the right to mint identities and write permissions. One credential that a dashboard, an auditor and a break-glass incident all had to share.

These are now separate powers, and a power is granted the way everything else here is granted: as a record, written by an operator, revocable, and visible in the same permissions answer above. observe reads everything and touches nothing. remediate unsticks work. sweep runs garbage collection. declassify clears the labels from the section on following data. purge destroys payloads. Two things are deliberately never powers: writing permissions themselves, and acting on records without a grant. Whoever can hand out authority holds every other power one step later, so that stays with the space's named operators.

The model you plug in over MCP holds the observe power by default and nothing else. It can look at anything, change nothing, and the credential behind it can be revoked like any agent's.

What this does not do

Being vague here would defeat the purpose, so plainly:

  • The checks live in the server. If you embed the runtime in your own process and call it directly rather than over HTTP, you are inside the boundary and nothing is enforced. Run the server.
  • Single sign-on covers people, not the root of trust. A space configured with an OIDC issuer mints ordinary sessions from a verified id_token (the console's "Sign in with SSO", radia login --sso), and deprovisioning at the identity provider ends access within one session ceiling. Operators stay a local config set: an IdP can never mint one.
  • There are no spending limits. You cannot yet say an agent may burn ten dollars an hour and no more.
  • The contents of a record are stored in the clear. They have to be, because that is what the routing matches on. Large payloads stored outside the record can be encrypted.
